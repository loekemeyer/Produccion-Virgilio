# Ideas del usuario — Producción Virgilio

Proyección en el repo de las ideas que **escribe el usuario** en cualquier chat.
Cada idea queda acá (durable, versionada) y además en la tabla `agente_propuestas`
(Supabase) para entrar al mismo circuito que las de los agentes: se desarrolla sola
en su rama `idea/<código>`, se recuerda en el Telegram de las 8 **todos los días
hasta que el usuario la active**, y se mergea a `main` cuando el usuario dice el número.

- `[ ]` = pendiente / esperando activación · `[x]` = activada (mergeada a main) ·
  `~~tachada~~` = descartada.
- El código de 4 dígitos es el mismo que en la tabla y en el Telegram.

> Este archivo es un espejo legible. La fuente operativa es la tabla
> `agente_propuestas`. Al registrar o activar una idea del usuario se actualizan
> los dos. No borres entradas: se tildan o se tachan.

- [ ] **8606** (2026-08-10) — **Picking siempre con la marca/variante correcta del código**. Que no se repita el error tipo 809/809E. **Causa raíz hallada:** el pipeline `reconciliar_pipeline_stock_etapa1()` saca el código del picking del **evento PKC** en `Registros_Produccion_Virgilio` (`texto = tanda|articulo|pedido|pickeado`; `art = split_part(texto,'|',2)`), NO de `PPP_Base_Pedidos`. Para split codes la app ya escribe la marca (ej. `438E CH`, `439E CH`), pero cuando el pedido referencia un código mal (`809` en vez de `809E`) la app escribe `809` sin E ni marca y el pipeline lo recrea siempre por la rama FORWARD (`do update`). Caso: `PKC D29A|809|14|14` debía ser `D29A|809E CH|14|14`. **Fixes:** (a) app: al pickear, resolver el código real (variante E + marca LK/CH por NP) antes de escribir el PKC, aunque el pedido traiga el código base/viejo; (b) upstream Sheet PPP: corregir NP 44566 a 809E; (c) opcional: `Equivalencias_Codigos` para mapear códigos viejos. El caso puntual D29A ya se corrigió a mano. — _pendiente_
